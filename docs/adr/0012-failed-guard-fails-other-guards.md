# 0012 落ちた guard は同じ commit の他の guard も失敗にする

- 状態: 採用
- 日付: 2026-11-27

## 背景

0009 で guard を 3 つのワークフローに置いた。PR が 1 つの guard を「何もせずに成功する」ように書き換えると、残りの 2 つは `.github/` の変更として落ちるが、PR のチェックには `guard` という名前の成功と失敗が並ぶ。チェックを名前ごとに 1 つの結果にまとめる集計(名前をキーにした辞書で後の結果が前を上書きするもの、GitHub の必須チェックのように同じ名前の最新の結果だけを見るもの)では、書き換えた方の成功が残り、`guard` が通ったことになる。カナリアの検査で、guard のジョブを 1 つだけ書き換えた PR が `guard` の失敗として扱われなかった。

書き換えられていない guard は、同じ base ブランチのスクリプトを同じ差分に走らせるので、結果は同じになる。同じ commit で 1 つの guard が落ち、別の guard が成功しているなら、成功した方は書き換えられている。

## 決定

- 各 guard ジョブに、判定の手順が落ちたときだけ走る(`if: failure()`)手順を足す。手順は base ブランチから取り出した `.github/scripts/guard_checks.py` を走らせる(0009 と同じく、PR のファイルや共有の action は使わない)。
- `guard_checks.py` は Checks API で次のことをする。
  1. 名前 `guard`、結果 failure のチェックを 1 つ足す。external_id に自分のワークフローの実行の ID を入れる。
  2. 同じ commit の他のワークフローの `guard` が終わるまで、最長 300 秒待つ。1. の印を付けた実行の guard は、落ちたと分かっているので待たない(落ちた guard どうしが互いを待ち続けないため)。
  3. 終わっていて成功(success、neutral、skipped)の `guard` を、failure に書き換える。書き換えを断られたら警告を出して続ける。
- guard ジョブにだけ `checks: write` の権限を与える。このリポジトリの PR は同じリポジトリのブランチから出すので、`pull_request` のジョブのトークンでもこの権限が使える。
- `.github/scripts/tests/test_workflows.py` が、すべての guard にこの手順と権限があることを確かめる。

## 結果

- 1 つの guard を書き換えた PR では、`guard` の名前のチェックがどれも失敗になるか、少なくとも最新の `guard` が失敗になる。名前ごとに 1 つの結果を見る集計でも、すべての結果を見る集計でも、`guard` は落ちる。
- 正しく違反を見つけた PR では、`guard` の失敗のチェックが 3 つ増える。guard が落ちるまでの時間は、他の guard が終わるのを待つ分(ふつうは数秒)だけ延びる。
- 3 つの guard をすべて書き換える PR は、0009 と同じく guard をすり抜けられる。CODEOWNERS の承認が無ければマージされない。
- Actions のジョブが作ったチェックを、ジョブのトークンで書き換えられるかは GitHub の扱いに依る。書き換えられない場合も、1. で足した失敗のチェックが最新の `guard` として残る。
