# 0018 ログアウトはセッションを捨てる。ログインが必要な画面はレイアウトで確かめる。デモのユーザーの名前に ID を付ける

- 状態: 採用
- 日付: 2026-11-27

## 背景

#122 で、ログアウト、ログインが必要な画面への案内、デモのユーザーの名前を作る。

- AC-F1-1: ログアウトすると、ログインが必要な画面を開けなくなる。
- AC-F1-2: ログインしていない状態でログインが必要な画面を開くと、ログイン画面へ案内される。
- AC-F2-3: デモのユーザーの名前は、一覧で互いに区別できる。
- AC-F2-4: 同じユーザーに戻る手段は持たない。もう一度ボタンを押すと新しいユーザーになる。

ログイン状態は Laravel のセッションで持ち、画面は Next.js がサーバー側で `GET /api/user` を呼んで確かめる(docs/adr/0015)。

## 決定

### ログアウト

- `DELETE /api/session` をログアウトの経路にする。`api` グループの中にあるので、CSRF の検証を通る(トークンが無い・偽物・他のサイトからのものは 419)。
- ログアウトは、セッションを丸ごと捨てて(`invalidate`)ID を作り直す。ログイン中の利用者はセッションにしか無いので、前の cookie では同じユーザーに戻れない。CSRF トークンも消え、次のリクエストで作り直される。
- ゲストが呼んでも 204 を返す。他の利用者のセッションには触れない。
- 画面は、ヘッダーのログアウトのボタンで `GET /api/csrf-token` のトークンを付けて呼び、成功したらトップを読み直す(サーバー側の描画のヘッダーをゲストの表示にするため)。
- 既存のユーザーとしてログインし直す経路は作らない。デモのボタンは毎回 `RegisterUser` で新しいユーザーを作る(docs/adr/0015)。

### ログインが必要な画面

- ログインが必要な画面は `/my` の下に置く。`app/my/layout.tsx` の `LoginGate` が、リクエストの cookie で `fetchCurrentUser` を呼び、ゲストなら `redirect("/login")` する。中身(`children`)はログインを確かめた後にだけ描くので、ゲストにワークスペースの中身は届かない。
- `LoginGate` は cookie を読むので `Suspense` の中に置く(Cache Components)。描画が始まってからの移動になるので、応答の状態は 200 のまま、ブラウザがログイン画面へ移る(Next.js 16 の認証の手引きと同じ形)。
- `proxy.ts` では確かめない。`proxy.ts` は `/api/*` の転送だけを受け持ち、ログイン状態の確かめ方を `fetchCurrentUser` の 1 つにまとめる。
- 画面での案内は表示のためで、データを守るのは Laravel の `auth` ミドルウェアである。後の issue が足す `/my` の API も、Laravel の側でログインと持ち主を確かめる。

### デモのユーザーの名前

- 名前は「役割の名前 + ` #` + ユーザーの ID」(例: `デモ読者 #12`)にする。`RegisterUser` で作った直後に、同じトランザクションの中で ID を足して保存する。
- ID は重ならないので、同じ役割のユーザーでも一覧で必ず見分けられる。無作為な文字列は短いと重なりうるし、長いと読みにくい。
- ID は利用者の数のおおよそを表すが、このアプリでは隠す必要が無い(ユーザーは毎日のリセットで消える)。

## 結果

- ログアウトした cookie でも、ログイン状態が切れた cookie でも、もう一度ボタンを押すと新しいユーザーになる。
- `/my` の下に画面を足す issue は、ログインの確かめを書かなくてよい。`/my` の外にログインが必要な画面を置くときは、同じ `LoginGate` を使う。
- デモのユーザーの名前の形が変わったので、名前の完全一致を確かめていた #121 のテストを、人間の承認を得て直した。
