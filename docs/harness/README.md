# ループ開発のしくみ

このリポジトリでは、人間がコードを読まずに、Claude Code または Codex CLI を繰り返し動かしてアプリを作る。この文書は、そのための道具立て(ハーネス)を人間向けに説明する。エージェントへの指示そのものは `AGENTS.md` にある。

## 何のためのものか

同じ要件書(`docs/requirements.md`)から、2つのリポジトリで同じアプリを作る。

- `novel-site-clone`: 人間がある程度コードを読んでレビューする。
- このリポジトリ: 人間はコードを読まない。正しいかどうかは CI だけで決める。

両者の速さ、費用、不具合の数を比べるのが目的。比べる意味があるように、このリポジトリでは人間の手をできるだけ入れない。人間が手を動かすのは、最初の準備と、エージェントが自分では決められないことを判断するときだけにする。

## 登場するもの

| 名前 | 正体 | 役目 |
|---|---|---|
| 人間 | あなた | 最初の準備をする。エージェントから上がってきた問題を判断する |
| まとめ役 | `scripts/loop/run.sh` | どの issue を誰にやらせるかを決め、エージェントを起動し、結果を見てラベルを付け替え、PR をマージする |
| エージェント | `claude -p` または `codex exec` の1回の実行 | 渡された1つの仕事(土台作り、計画、1つの issue の実装など)をして終わる。毎回まっさらな状態で始まる |
| GitHub | issue、PR、CI、ブランチ保護 | 仕事の一覧と進み具合を持つ。CI が合否を決める |

まとめ役は普通のシェルスクリプトで、判断はしない。決まった手順どおりに、エージェントを起動し、その最後の一行(`RESULT: ...`)を読んで次に進む。合否の判断は CI と、まとめ役が呼ぶ検査用のスクリプトがする。エージェントの自己申告は信用しない。

## 実行する CLI の選択

土台作り(カナリアを含む)と計画の CLI は、ループ起動時の `LOOP_AGENT` で選ぶ。省略すると Claude を使う。Codex を使う場合は `CODEX_MODEL` に使用可能なモデル ID を指定する。1 セッションの実行時間は `CODEX_MAX_SECONDS` で変えられる(既定は 1800 秒)。以下の `plan` は `bootstrap` にも置き換えられる。

```bash
LOOP_AGENT=codex CODEX_MODEL="<利用するモデル ID>" CODEX_MAX_SECONDS=1800 scripts/loop/ctl.sh start plan
```

機能 issue の実装とレビューは `LOOP_AGENT` ではなく、`work` の引数で選ぶ(「ワーカーを選ぶ」を参照)。

まとめ役は1つにして、Claude と Codex の比較に同じ issue の状態遷移と CI の基準を使う。CLI ごとの起動引数、操作の表し方、出力形式はまとめ役との境界で変換し、生ログも残す。Claude は API 換算額の上限で止める。Codex CLI には同じ USD の上限がないので、指定した秒数でプロセスを止め、同じセッションの再開分は合算する。

Codex CLI 0.172.0 の `exec --json`、`exec resume`、`app-server` の `hooks/list` を使う。選んだ CLI をログイン済みにし、worktree で Git、GitHub CLI、Docker Compose を利用できるローカル実行環境を使う。CLI の実行中に上限へ達するとプロセスを終了する。上限は同じセッションの再開分を合計し、利用上限の解除待ちと一時エラーの再試行待ちは含めない。Codex の料金上限は保証しない。

Codex の各回の生ログは `*.partN.raw.jsonl`、共通の判定用ログは `*.jsonl` に記録する。メトリクスには実行した CLI、モデル、取得できたトークン数を含める。Codex の USD は `null`（不明）として集計し、Claude の費用には CLI が報告した API 換算額を使う。エージェントの切替はループ起動時に行い、中断したセッションを別の CLI で再開することはできない。

共通の回帰テストは `python3 scripts/loop/test_agents.py` で実行する。GitHub への接続は不要。

## 全体の流れ

```
[人間] 最初の準備
   │
   ▼
① 土台作り(bootstrap) ── アプリの骨組みと CI を作る
   │   CI そのものが正しく働くかを、わざと悪い PR を出して確かめる
   ▼
② 計画 ── 要件書を issue に分ける
   │   検査スクリプトと、別のエージェント(批評役)が確かめる
   ▼
③ 実装 ── issue を1つずつ TDD で実装し、リファクタリング後にローカルで検証する
   │   ↺ 分け方が悪かった issue は、②に戻して分け直す
   ▼
④ レビュー ── 別のエージェントがブランチの差分をレビューし、実際に起こりうる重要な不具合だけを直す
   │   まとめ役が PR を作り、レビュー済みコミットの必須 CI が通ったらマージする
   ▼
すべての issue が閉じたら終わり
```

途中でエージェントが自分で決められないことにぶつかると、その issue に `loop:escalated` を付けて止まる。人間がそれを見て判断する。

## 各段階の中身

### 最初の準備(人間が1回だけ)

人間が書いて固定するもの。エージェントはこれらを変えられない。

- `AGENTS.md`: エージェントが守る規則
- `docs/requirements.md`: 何を作るか
- `scripts/loop/` 以下: まとめ役、各段階でエージェントに渡す指示文、設定値、依存の許可リスト、カナリア(後述)の検査と判定のスクリプト、保護のための hook
- `.github/ISSUE_TEMPLATE/feature.md`: issue の書式。検査スクリプトがこの見出しを読む

アプリの骨組みも人間が用意する。設計の判断を含まない機械的な作業で、しかも先に Docker で動くことを確かめておけば、土台作りで無駄な試行錯誤をさせずに済むからである。

- 開発用の Docker 環境(`compose.yaml`、`docker/`、`.env.example`): `novel-site-clone` からコピーし、Compose のプロジェクト名だけを変えた(同じ名前だと、人間の版のコンテナとボリュームを取り合う)。人間の版での設計(Redis、キャッシュの破棄、デモのレート制限の環境変数など)もそのまま含んでいる
- `backend/`: `composer create-project laravel/laravel`(Laravel 13)をそのまま。生成された Laravel Boost の案内文(`AGENTS.md`、`CLAUDE.md`)は、ホストへの PHP のインストールや許可リストにない依存の追加を指示するので削除した
- `frontend/`: `create-next-app`(Next.js 16.4.6、TypeScript、ESLint、App Router、Tailwind なし)をそのまま

このため、ループの所要時間と費用には、Docker 環境と骨組みを作る分が入っていない。人間の版と比べるときは、この点を差し引いて考える。

そのうえで、GitHub にリポジトリを作り、`scripts/loop/setup-github.sh` でラベルとブランチ保護と土台作りの issue を作る。

### ① 土台作り(bootstrap)

最初のエージェントが、人間の用意した骨組みの上に、テストの道具(Pest、Larastan、Infection、Vitest、Stryker、Playwright)、worktree ごとの環境を作るスクリプト、CI をまとめて作る。普段は変更を禁じている CI やテストの設定も、この回だけは作ったり変えたりしてよい。

1つのセッションでは大きすぎるので、次の段階に分け、段階ごとに別のセッションと予算(`MAX_COST_USD_BOOTSTRAP_STAGE`)を割り当てる。どの段階も同じブランチと同じ PR に積み上げる。

| 段階 | すること |
|---|---|
| `tooling` | テストの道具と、worktree ごとの環境を作るスクリプト |
| `ci-checks` | CI のジョブ `backend` `frontend` `e2e` `mutation` `visual` |
| `ci-guard` | CI のジョブ `ac-coverage` `guard`(ずるの検出、保護パス、依存の許可リスト) |
| `finish` | metrics のワークフロー、PR のひな形、CODEOWNERS、文書。PR を開く |

`finish` と `fix-*` のエージェントは push して PR を開いたら、CI を待たずに終わる。CI の結果はまとめ役が待つ。必須のジョブが落ちたら、落ちたジョブと、この土台作りでの CI の履歴(`../loop-novel-site-clone.loop/bootstrap-ci-history`)を添えて、新しいセッションで直させる。履歴のたまった重い会話のまま CI を待つと、待つだけのターンでも毎回その会話を読み直す費用がかかるので、待つ役をまとめ役に移した。直したはずのセッションが何も push しなかったときと、1つの段階で `MAX_ATTEMPTS` 回 push しても緑にならないときは、人間の判断待ちにする。

段階を積み終えたらカナリアで確かめる。不合格のときは、不合格のケースを担当ごとに分け(`fix-checks` と `fix-guard`)、担当ごとに別のセッションで直してから、もう一度カナリアで確かめる。

途中で止まっても、`ctl.sh start bootstrap` で起動し直せば、終わった段階とカナリアの round を飛ばして続きから始まる。終わった段階は `../loop-novel-site-clone.loop/bootstrap-stages.done` に記録される。

問題は、エージェントが作った CI をどう信用するかである。人間がレビューする代わりに、**カナリア**で確かめる。カナリアとは、わざと規則を破った PR のこと。たとえば次のようなもの。

- テストを飛ばす `test.skip` を入れる
- 型の検査を黙らせる `@ts-ignore` を入れる
- 既にあるテストの期待値を書き換える
- テストの無い分岐を足す
- 許可していない依存を足す

カナリアには人間は関わらない。代わりに、次のことを機械的に守らせる。

| 守りたいこと | どう守るか |
|---|---|
| CI を作る役と、CI を試す役が別である | カナリアの仕様は、土台作り役とは別のエージェント(仕様役)が書く。PR を出すのも別のエージェント(適用役)。合否はスクリプトが決める |
| 試す内容が、CI を作る前に決まっていて、後から変えられない | 仕様役は土台作りが始まる前に仕様を書く。まとめ役はその時点で仕様のハッシュ値を issue にコメントし、以後、仕様が変わっていないかを毎回確かめる |
| 土台作り役が、試す内容を見られない | 仕様はリポジトリの外に置く。作業中の見張り(hook)が、土台作り役によるカナリアの読み取りや検索を、実行する前に止める。食い違いを伝えるときも、カナリアの差分は渡さず、どの規則が守られていないかだけを伝える |
| 規則に抜けがない | `AGENTS.md` の禁止事項、保護するファイル、CI の検査、依存の規則の箇条書きすべてに番号を振り、どれも1つ以上のカナリアで試されていることをスクリプトが確かめる。正しい変更が通ることを確かめるケースも必須 |
| 合否をエージェントが決めない | 判定は `scripts/loop/canaries.py` がする |

流れは次のとおり。

1. 仕様役が、`AGENTS.md` だけを読んでカナリアの仕様を書く。スクリプトが抜けを調べ、通ったら固定する。
2. 土台作り役が骨組みと CI を作り、その PR の CI を通す。
3. 適用役が、仕様どおりにカナリアの PR を出す。
4. スクリプトが結果を判定し、カナリアの PR を閉じる。すべて期待どおりなら、土台の PR をマージし、仕様と結果を PR に公開する。
5. 食い違ったら、どの規則が守られていないかを土台作り役に伝えて、2 からやり直す。

同じカナリアが何回も続けて食い違うときは、CI が悪いのか、カナリアの方が無理を言っているのかを、さらに別のエージェント(判定役)が決める。判定役は、CI の中身は見ずに、規則とカナリアの差分と結果だけを見て、「CI を直すべき」「カナリアを書き直すべき」「その規則はそもそも CI では確かめられない(免除)」のどれかを選ぶ。免除した規則は理由とともに記録する。

決められた回数をやり直しても合わないときだけ、人間に上げる。

### ② 計画

計画役のエージェントが、要件書を issue に分ける。各 issue には次のことを書く。

- 満たす受け入れ条件の ID(`AC-F5-1` など)
- 先に終わっている必要がある issue
- 触りそうなファイル
- やること、やらないこと

分けた結果は、人間ではなく2段階で確かめる。

1. **検査スクリプト**(`scripts/loop/validate-plan.sh`): すべての受け入れ条件がちょうど1つの issue に入っているか、依存が輪になっていないか、触るファイルが重なる issue どうしに順番が付いているか、などを機械的に調べる。
2. **批評役のエージェント**: 計画を書いていない別のエージェントが、要件書と見比べて、1回で終わらない issue や、抜けている依存を指摘する。

指摘があれば計画役が直す。決められた回数のうちに両方を通れば、まとめ役が issue に `loop:ready` を付ける。

### ③ 実装

まとめ役は、`loop:ready` が付いていて、依存する issue がすべて閉じているものを1つ選び、専用の作業場所(git の worktree)を作ってエージェントを起動する。1回の実行で1つの issue を実装し、1つの PR を出す。

エージェントは次の順で進める。

1. テストを先に書いて、落ちることを確かめる
2. テストが通る最小のコードを書く
3. 整理して、またテストを通す
4. ローカルでコミットし、PR 本文の下書きをレビュー役に引き継ぐ

push と PR 作成はレビュー後にまとめ役が行う。

レビューが終わったら、まとめ役は push の前に最新の main をブランチに取り込む。実装している間に別の issue がマージされていても、最初の CI から最新の main で確かめられる。取り込みが衝突したら、CI を回さずに実装役へ戻す(3回続けば人間の判断待ちにする)。

CI が通ったら、まとめ役は main に入れる前に、ブランチが main に追いついているかをもう一度確かめる。ブランチ保護が strict(main に追いついていないブランチはマージできない)なので、並列で動かして別の issue が先にマージされると、そのままではマージできない。

- 追いついていれば、そのままマージする。
- main が先に進んでいれば、main をブランチに取り込んで push し、その commit の CI が通るのを待ってからマージする。取り込みは main の変更を足すだけで、レビュー済みの差分は変わらないので、レビューはやり直さない。
- 取り込みが衝突したとき、または取り込んだ後の CI が落ちたときは、試行を1つ進めて実装役に戻す。理由は CI の履歴(`<STATE_DIR>/issue-<番号>-ci-history`)に書くので、実装役はそれを読んで直し、またレビューを通る。
- マージは、確かめた commit と PR の head が同じときだけ行う(`--match-head-commit`)。確かめた直後に main が進んで断られたら、取り込みからやり直す(5回まで)。worktree はマージに成功してから片付ける。

### マージ前のレビュー

実装していない別セッションのレビュー役が、デフォルトブランチとの分岐点から HEAD までの差分と、その呼び出し元・テストをローカルで調べる。

レビューでは細かい指摘も多く出るが、直すのは次の3つをすべて満たすものだけにする。

- この変更が持ち込んだ、または悪化させた不具合である(元からあった不具合や、書き方の好みではない)
- 確かに起こると確認できている
- 要件書どおりに使われるこのアプリで、実際に起こりうる(ありえない入力や、範囲外の環境でしか起きないものではない)

直すときも TDD で進める。まず指摘の不具合を再現するテストを書き、落ちることを確かめてから直す。修正後は該当テストをローカルで再実行する。

レビュー役は指摘と対応理由を記録する。修正後は最大 `MAX_REVIEW_ROUNDS` まで再レビューし、まとめ役がレビュー済みコミットを push、PR を作成してレビュー記録をコメントする。必須 CI が失敗した場合は、失敗したジョブとリンクを実装役へ戻し、ローカル修正・レビューの後で同じ PR を更新する。成功時は実行・成果物のリンクを PR に加え、確認したコミット SHA を指定してマージする。

細かい指摘まで直させないのは、直すたびに新しい不具合が入る危険と、手間とが増えるからである。

### 分け直し

実装の途中で「この issue は1つの PR に収まらない」「別の issue と同じファイルを触る」などと分かったら、エージェントは人間に上げずに `loop:replan` を付けて止まる。まとめ役は、ほかの実装が終わるのを待ってから、分け直し役のエージェントを起動する。分け直した結果も、②と同じ2段階の確認を通す。

## ラベルの意味

| ラベル | 意味 | 付けるのは |
|---|---|---|
| `loop:bootstrap` | 土台作りの issue | 人間(準備のスクリプト) |
| `loop:planned` | 計画したが、まだ確認を通っていない | 計画役 |
| `loop:ready` | 確認を通り、着手してよい | まとめ役だけ |
| `loop:in-progress` | エージェントが作業中 | まとめ役だけ |
| `loop:replan` | 分け方が悪く、分け直しが要る | 実装役 |
| `loop:escalated` | 人間の判断が要る | エージェントかまとめ役 |
| `loop:canary` | カナリアの PR。マージしない | 適用役 |

## ずるを防ぐしくみ

人間がコードを読まないので、エージェントが「正しく作る」のではなく「検査を通すだけ」に走ることを防ぐ必要がある。そのために4重の守りがある。

1. **規則**(`AGENTS.md`): テストを飛ばす、検査を黙らせる、テスト環境でだけ動きを変える、といった行為を禁じている。
2. **作業中の見張り**(`scripts/loop/guard-hook.py`): エージェントがファイルを書き換えようとするたびに呼ばれ、守るべきファイル(既存のテスト、検査の設定、規則、要件書など)への変更をその場で止める。まとめ役が毎回外から差し込むので、エージェントが外すことはできない。シェルのコマンドについては推測で判定しているので、抜け道は残る。
3. **CI**: テスト、静的解析、E2E テスト、ミューテーションテスト(コードをわざと壊して、テストがそれを見抜けるかを試す)、見た目の比較、受け入れ条件ごとのテストの有無、禁止パターンの検出。最後の砦はここ。
4. **ブランチ保護と CODEOWNERS**: CI が通らない PR はマージできない。守るべきファイルを含む PR は、人間の承認がないとマージできない。

そして、3 の CI が本当に働いているかは、土台作りのときにカナリアで確かめておく。

### CI のジョブ

土台作りで作った CI は、PR ごとに次の7つのジョブを走らせる。どれもブランチ保護の必須チェックで、1つでも落ちるとマージできない。設計の理由は `docs/adr/0003`〜`0005`、`0007`、`0009`〜`0011` にある。

1つの違反は、なるべくその規則を受け持つ1つのジョブで落とす。たとえばテストを飛ばす書き方や `eslint-disable` のコメントは guard だけが止め、`backend` や `frontend` はそれらを理由に落ちない。どのジョブが落ちたかを見れば、どの規則を破ったかが分かるようにするためである。

同じ理由で、変更と関係の無いジョブがダウンロードの失敗で落ちないようにしている。多くの PR が同時に走っても GitHub の上限に当たらないよう、`composer install` にはジョブの読み取りだけのトークンを渡す。さらに、どのブランチへの push でも `Composer cache` のワークフロー(必須チェックではない)がそのブランチに composer のキャッシュを作り、そのブランチに向けた PR のジョブはそれを読んでパッケージをほとんど取りに行かない。

| ジョブ | 何をするか | 何を見つけるか |
|---|---|---|
| `backend` | Pest(`arch()` テストを含む)、PHPStan(レベル max、baseline なし)、Pint | バックエンドの不具合、型の誤り、書式の乱れ。`arch()` テストは、`declare(strict_types=1)` の書き忘れ、アプリのコードから `env()` を直接読むこと、デバッグ用の関数の残りなどを見つける。何も確かめないテストと警告も失敗にする |
| `frontend` | Vitest、ESLint、型検査(`tsc`)、`next build` | フロントエンドの不具合、型の誤り、ビルドできない変更。ESLint は `any` と、ネットワークからフォントを取る `next/font/google` を禁じる。確認の無いテストと `.only` の取り残しも失敗にする |
| `e2e` | Docker Compose でアプリを起動し、Playwright で画面を操作する | 利用者から見た動きの不具合。動画とスクリーンショットを artifact に残す |
| `visual` | Playwright で画面を撮り、リポジトリにある基準画像と比べる | 見た目が意図せず変わったこと。画面のファイルを変えたのに基準画像を足しも変えもしない PR も落とす |
| `mutation` | Infection(PHP)と Stryker(TypeScript)で、PR が変えた行だけをわざと壊し、テストが気づくかを試す | テストの無い分岐、弱すぎる確認。壊したもののうち見つけられた割合がしきい値(Infection は 80%、テストが通る行に限れば 90%。Stryker は 80%)を下回ると落ちる |
| `ac-coverage` | PR の本文の `AC:` 行の受け入れ条件の ID ごとに、その ID を付けたテストがあるかを、各テストツールに一覧を出させて確かめる | テストの無い受け入れ条件。`AC:` 行が無い、要件書に無い ID がある、閉じる issue の ID と合わない PR も落とす |
| `guard` | PR の差分を読み、追加された行の禁止パターン、保護されたファイルの変更、依存の変更を調べる | テスト環境での特別扱い、テストの入力にだけ期待どおりの値を返すコード(テストの入力と期待値の両方を本番のコードに書き込んだ分岐)、テストの題名を本番のコードに書くこと、テストを飛ばす書き方、検査を黙らせるコメント、失敗しようのない確認、テストでの再試行や待ち時間、既存のテストや検査の設定や規則の変更、許可リストに無い依存や範囲を超える版の追加 |

guard、ac-coverage、mutation、visual が使う判定のスクリプト(`.github/scripts/`)は、PR の版ではなく、マージ先のブランチにある版を使う。PR がスクリプトを書き換えて検査をすり抜けるのを防ぐためである。スクリプトそのものの試験も guard の最初に走る。

guard は、`.github/workflows/guard.yml`、`ci.yml`、`ac-coverage.yml` の3か所に同じものを置いている。そのため PR のチェックには `guard` が3つ並ぶ。GitHub Actions は PR の版のワークフローで動くので、PR は guard のジョブを「何もせずに成功する」ように書き換えられる。それでも残りの guard がその書き換えを保護されたファイルの変更として落とす。1つのファイルを書き換えて3つとも止められないよう、各 guard は共有のスクリプトを使わず、手順を自分の中に書いている。マージ先のブランチの版のワークフローで動く `pull_request_target` は、GitHub の仕様で既定のブランチ(main)の版しか使われず、公開リポジトリでは 2026-12-02 から止められるので使わない。

ミューテーションテストは、PR が変えた行だけをわざと壊す。PHP の Infection は Pest に直接対応していないので、`backend/tests/bin/pest-for-infection.php` が Pest を PHPUnit に見せかけている。この包みが正しく動かないと、テストが通ってもすべての変異が「見つかった」ことになり、弱いテストを見逃す(土台作りの途中で実際に起きた)。

保護されたファイルの判定は、マージ先に `.github/CODEOWNERS` があるときだけ行う。土台作りの PR は、マージ先の main にまだ CODEOWNERS が無いので、この判定を受けない(土台作りだけは保護されたファイルを作ってよいため)。

## 人間に回ってくるとき

エージェントは次の場合に止まり、issue に `loop:escalated` を付けて、試したこと、失敗した検査とエラー、止まった理由、人間に決めてほしいことをコメントに書く。

- 要件書の受け入れ条件があいまい、または互いに食い違う
- 既にあるテストを変えないと進めない
- 既にあるテーブルや列を変える、または消すマイグレーションが要る
- 許可リスト(`scripts/loop/dependencies.md`)にない依存が要る
- 過去の設計判断(`docs/adr/`)と食い違う
- カクヨムの画面で、承認が要る操作をしたい(`docs/kakuyomu-reference.md`)
- 同じ検査が同じエラーで3回続けて落ちた、2回続けて変更がほとんど進まなかった、試行回数か費用の上限に達した

人間は、コメントを読んで判断し、必要なら要件書や規則を直す。そのあと `loop:escalated` を外して `loop:ready` を付け直せば、次の実行で続きから再開する。作業途中のブランチは残っているので、エージェントはそこから続ける。

## 動かし方

```bash
# 1. scripts/loop/config の CODEOWNER に自分の GitHub のユーザー名を入れる
# 2. git の初期化、GitHub へ push
git init -b main && git add -A && git commit -m "初期設定"
gh repo create <名前> --private --source . --push
# 3. ラベル、ブランチ保護、土台作りの issue を作る
scripts/loop/setup-github.sh
# 4. 最初は土台作りだけを動かして、結果を確かめる
scripts/loop/ctl.sh start bootstrap
# 5. 問題なければ、計画と実装へ
scripts/loop/ctl.sh start plan
scripts/loop/ctl.sh start work
```

`scripts/loop/ctl.sh start all` は、土台作り、計画、実装を止まらずに続けて行う。`ctl.sh start` は `run.sh` に同じ引数を渡し、裏で(`setsid nohup`)起動する。ログは `../loop-novel-site-clone.loop/<引数>-run.log` に出る。前のログがあれば、日時を付けた名前に変えて残す。すでに動いていれば、2つ目は起動しない。

### 動いているかを確かめる

```bash
scripts/loop/ctl.sh status   # 1行目が 動作中 / 待機中 / 人間待ち / 完了 / 停止 のどれか
scripts/loop/ctl.sh watch    # ログと状態を流し続ける
scripts/loop/ctl.sh stop     # run.sh と子のエージェントをまとめて止める
```

`run.sh` は段階を移るたびに `../loop-novel-site-clone.loop/status/` に状態を書く。`run.json` が起動と終わり方、`main.json`(並列の issue は `issue-<番号>.json`)がその時点の段階(エージェント実行中、CI 待ち、カナリアの判定待ち、利用上限のリセット待ち、人間待ち、完了、停止)。`status` はこれと `run.sh` のプロセスが生きているかを合わせて表示するので、kill や異常終了で記録が途切れても「停止」と分かる。

Orca から起動したときは、Orca の画面にも出す。表示のためだけなので、Orca がなかったり呼び出しに失敗したりしても、ループは止まらない。

- メインのチェックアウトのワークスペースに `loop: <引数>` のタブを開き、`watch` を流す。タブ名は状態に合わせて変わる(`loop ▶ エージェント実行中 …`、`loop ⏳ CI 待ち …`、`loop ⚠ 人間待ち` など)。タブは見るためだけのもので、閉じてもループは止まらない。`ctl.sh start` をやり直せば開き直す。
- ワークスペースのボードの状態とコメントを、ループの状態に合わせる。人間待ちと停止のときは `in-review` にして未読の印を付ける。
- エージェントを1回起動するたびに、その worktree(`../loop-novel-site-clone.loop/worktrees/` の下。Orca が作ったものではないので、`ctl.sh start` が表示を有効にする)にタブを開き、ツールの呼び出し、失敗、最後の RESULT と費用を流す。同じ worktree の前回のタブは閉じる。中身は `../loop-novel-site-clone.loop/logs/` の記録と同じ。

`work` は、着手できる issue がなくなると止まる。全部終わったときは終了コード 0、人間の判断待ちの issue が残っているときは 2 を返す。

## 利用上限に当たったとき

claude.ai のサブスクリプションで動かすと、5時間ごとや週ごとの利用上限に当たって、エージェントが途中で止まることがある。まとめ役はこれを人間の判断待ちにはせず、次のように扱う。

1. 選択した CLI の出力から、上限に当たったことと、上限が明ける時刻を読み取る。時刻が分からなければ30分待つ。
2. 明ける時刻まで待つ。待っている間は、新しい issue に手を付けない。
3. 同じセッションを再開(resume)し、「待っている間に状況が変わっているかもしれないので、CI や PR の状態を確かめてから続けて」と伝える。

待つのは最長8日まで(`RATE_LIMIT_MAX_WAIT_HOURS`)。それより先にしか明けないときは、あきらめて人間の判断待ちにする。混雑やネットワークの不調など一時的なエラーのときは、5分おきに3回までやり直す。

## ワーカーを選ぶ

`scripts/loop/ctl.sh start work codex` は、同じ Issue の実装もレビューも Codex で行う。レビューは新しいセッションを使う。`work claude`（引数を省略した場合も同じ）は両方に Claude を使う。`work mixed` は1つのまとめ役の中で、着手順に Claude、Codex と交互に Issue を割り当てる。並列数は従来どおり config の PARALLELISM に従う。Issue の二重取得を避けるため、同じリポジトリでまとめ役を複数起動しない。

Claude は実装・レビューともに `claude-opus-5-5` を使い、実装の推論量は `medium` とする。Codex の実装は `CODEX_IMPLEMENTATION_MODEL`(既定は `gpt-6.2-sol`)の `medium`、レビューは `CODEX_REVIEW_MODEL`(既定は `gpt-6.2-astra`)を使う。どちらのワーカーも実装役が差分と影響範囲を見て、認可・公開範囲・並行更新に関わる場合はレビューを config の `REVIEW_LEVEL`(既定は `high`)で、通常は `medium` で行う。分類が欠けるか不正なら `REVIEW_LEVEL` を使う。実行ログの先頭には CLI、モデル、推論量を記録する。

Claude の推論量は、bootstrap の各段階とカナリアの仕様・適用・判定が `medium`(config の `BOOTSTRAP_EFFORT`)、計画と批評が `high`(`EFFORT`)とする。

Codex の実行にはログイン済みの Codex CLI と、worktree で Docker・Git・GitHub を利用できる権限が必要。起動時に、メインチェックアウトの `guard-hook.py` が信頼済みとして有効になることを確かめる。設定できなければ作業を始めない。`workspace-write` と承認不要の設定を指定し、ネットワークを許可する。worktree に加え、コミットに必要な Git の管理ディレクトリ、PR 本文・レビュー報告の受け渡し先、この実行専用の `TMPDIR` に書き込める。

Claude と同じように、`ctl.sh status` と Orca に実行中の作業を表示する。Orca の実行タブでは Codex の生ログを流し、実行が終わるとタブの表示を終了する。一時ディレクトリを消し、古くなった worktree の登録も片付ける。

Codex が利用上限や一時エラーで中断したら、セッション ID がある場合に同じセッションを再開する。上限の解除時刻を取得できないときは config の待ち時間を使う。一時エラーの再試行回数も config に従う。`CODEX_MAX_SECONDS` は実装・各レビューごとに適用し、再開分も合算する。解除や再試行を待つ時間は含めない。時間切れでは Codex のプロセスを止める。再開できない異常終了や時間切れでは、その実行を記録して Issue を escalation する。

## 記録

Codex は実装・各レビューにつき1行を `<STATE_DIR>/metrics/<Issue番号>.jsonl` に追記する。UTC の開始・終了時刻、CLI が動いた時間(ミリ秒)、役割、モデル、推論量、最後の終了コード、再開回数を記録する。同じセッションの再開分は1行にまとめる。トークン数は CLI の `turn.completed.usage` に基づく。`input_tokens` は `cached_input_tokens` を含むため、総量は入力と `output_tokens` の和。利用量が届かなければ null、異常終了した回や一部欠落があれば `usage_complete: false` になる。別セッションは新しい行に追記し、過去のログは再集計しない。マージ前には Claude と同じ経路で PR に転記する。

土台作り・実装・レビューの担当は、テストや CI のログの取得を `scripts/loop/check-output.sh` 経由で実行する。CI の完了はどの担当も待たず、まとめ役が待つ。会話には終了コードとログのパスを1行で返し、失敗時にはエラー周辺（見つからなければ末尾）を添える。標準出力と標準エラーの全文は実行ごとに一時ディレクトリの別ファイルに残る。

- エージェントの1回ごとの実行記録は `../loop-novel-site-clone.loop/logs/` に残る。再開した場合も、1つのファイルにつなげて残す。
- 各実行の行には、動かしたエージェント(`agent`)、モデル(`model`)、推論量(`reasoning_effort`)が入る。まとめ役が起動時の値を実行記録の先頭(`loop_meta`)に書き、そこから読む。`ctl.sh status` と Orca の表示にも、実行中のモデルと推論量が出る。
- 計画・批評・分け直しの各実行は issue に属さないので、`<STATE_DIR>/metrics/plan.jsonl` に1行ずつ記録する。`run` は `plan-r<回>`、`plan-critic-r<回>`、`replan-r<回>`、`replan-critic-r<回>`。PR には転記されないので、集計するときはこのファイルも読む。
- 人間の判断を求めた回数(escalation)は、`<STATE_DIR>/metrics/escalations.jsonl` に1回1行で記録する。項目は時刻(`at`、UTC)、`issue`(計画の escalation では null)、`source`(まとめ役が止めたら `orchestrator`、エージェントが自分で止まったら `agent`)、`reason`。計測は土台作りが終わってから始め、`run.sh bootstrap` の中の escalation は数えない。
- まとめ役は、マージの直前に、その issue にかかった時間、やりとりの回数、トークン数、CLI が報告した API 換算額、再開した回数を PR にコメントで残す。CI がそれを `metrics` ブランチの `metrics/metrics.jsonl` に書き足す。比較にはこれを使う。

### metrics の読み方

`metrics/metrics.jsonl` は、マージされた PR 1つにつき1行の JSON である(`.github/workflows/metrics.yml`、`docs/adr/0006`)。見るには `git fetch origin metrics && git show origin/metrics:metrics/metrics.jsonl` とする。

| 項目 | 意味 |
|---|---|
| `pr`、`issue`、`title`、`branch` | PR の番号、閉じた issue の番号、題名、ブランチ |
| `created_at`、`merged_at` | PR を開いた時刻とマージした時刻(差がおおよその所要時間) |
| `attempts` | 試行の回数。CI が走った push の数 |
| `ci_runs`、`ci_failures` | CI の実行回数と、そのうち落ちた回数 |
| `totals` | まとめ役のコメントの合計。`api_equivalent_cost_usd` は API に換算した費用、`duration_ms` はエージェントが動いた時間、`num_turns` はやりとりの回数、`resumes` は再開の回数 |
| `runs` | 実装、レビューなど、実行ごとの内訳 |
| `metrics_comment_found` | まとめ役のコメントが見つかったか。`false` なら `totals` は 0 |

土台作りの PR では、`runs` に仕様役、土台作り役、適用役、判定役の各回が並ぶ。

## わかっている問題

- **利用上限の検出**: 上限に当たったことは、Claude Code が出す `rate_limit_event` とエラーの文言から見分けている。偽の Claude Code を使った試験では動いたが、本物の上限に当たったときの出力では、まだ確かめていない。見分けられなかった場合は、従来どおりその issue が人間の判断待ちになる。
- **費用の上限**: `MAX_COST_USD` は API に換算した額で、サブスクリプションで実際に払う額ではない。サブスクリプションのときにこの上限が効くかどうかは、まだ確かめていない。また、resume した実行の費用が、その回の分だけなのか、セッション全体の累計なのかも確かめていない。累計だった場合は、合計を多めに数えることになる(止まるのが早くなる方向なので、危険はない)。
- **ブランチ保護**: 「承認は不要、ただし守るべきファイルを含むときは CODEOWNERS の承認が要る」という設定が、意図どおりに効くかはまだ確かめていない。また、PR を出すのは自分のアカウントなので、守るべきファイルを含む PR は自分では承認できず、管理者としてマージすることになる。
- **並列実行**: ブランチ保護で「main に追いついていること」を求めているので、並列数を2以上にすると、先にマージされた変更に追いつけずにマージが失敗する。いまは並列数1で動かす前提。
- **シェルの見張り**: 作業中の見張りは、シェルのコマンドについては文字列から推測しているだけで、抜け道がある。最後に止めるのは CI である。
- **CODEOWNERS と既存のテスト**: CODEOWNERS は「既存のファイルだけ」を指定できない。テストのフォルダを丸ごと指定すると、テストを足すだけの PR まで人間の承認が要り、ループが止まる。そこで、土台作りの時点にあったテストと ADR だけをファイルごとに書いている。その後に足されたテストの書き換えは、CODEOWNERS ではなく guard ジョブだけが止める。
- **ワークフローの書き換え**: GitHub Actions は、`pull_request` では PR の版のワークフローを使う。`backend` や `mutation` などのジョブは、PR がワークフローを書き換えればすり抜けられる。guard も、3か所すべてを書き換えればすり抜けられる。どれか1か所だけを書き換えた場合は残りの guard が `.github/` の変更を落とす。どの場合も CODEOWNERS の承認が要るので、マージはされない。
- **特別扱いの判定は形の照合**: 「テストの入力 X なら期待値 Y を返し、それ以外は計算する」形を、`if`、三項演算子、`switch` の `case`、PHP の `match`(`default` が計算するもの)で探し、X と Y が PR の変えたテストに現れるときだけ止める。配列やオブジェクトの対応表を引いてから計算に回す書き方は見つけられない。逆に、正当な分岐でも、比べる値と返す値がどちらもテストに出てきて、それ以外で計算した値を返すと止まる。そのときは、特別な値も一般の計算で求めるように書き直す。
- **骨組みの画面の基準画像**: 土台作りでは、Next.js の骨組みのトップページの見た目を基準画像にしている。トップページを作り替える最初の issue は、この基準画像を変えることになり、人間の承認が要る。
- **guard の判定は文字列の照合**: 禁止パターンは正規表現で探しているので、書き方を変えればすり抜けられる場合がある。逆に、本番のコードで `'test'` のような文字列を正当に使う場合も止まる。
- **カナリアの隠し方**: 閉じたカナリアの PR は GitHub 上に残る。土台作り役が PR の一覧を取れば、題名は見えてしまう。差分を開く操作は見張り(hook)が止めるが、題名だけから察することまでは防げない。以前は実行記録を後から調べてカナリアに触れた回を無効にしていたが、hook が止めた操作や、まとめ役が渡したケース名をメモに書いただけの操作まで違反とみなし、作業が止まったのでやめた。
