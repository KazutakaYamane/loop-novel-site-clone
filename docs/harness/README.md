# ループ開発のしくみ

このリポジトリでは、人間がコードを読まずに、Claude Code を繰り返し動かしてアプリを作る。この文書は、そのための道具立て(ハーネス)を人間向けに説明する。エージェントへの指示そのものは `AGENTS.md` にある。

## 何のためのものか

同じ要件書(`docs/requirements.md`)から、2つのリポジトリで同じアプリを作る。

- `novel-site-clone`: 人間がある程度コードを読んでレビューする。
- このリポジトリ: 人間はコードを読まない。正しいかどうかは CI だけで決める。

両者の速さ、費用、不具合の数を比べるのが目的。比べる意味があるように、このリポジトリでは人間の手をできるだけ入れない。人間が手を動かすのは、最初の準備と、エージェントが自分では決められないことを判断するときだけにする。

## 登場するもの

| 名前 | 正体 | 役目 |
|---|---|---|
| 人間 | あなた | 最初の準備をする。エージェントから上がってきた問題を判断する |
| まとめ役 | `scripts/loop/run.sh` | どの issue を誰にやらせるかを決め、エージェントを起動し、結果を見てラベルを付け替え、PR をマージする |
| エージェント | `claude -p` の1回の実行 | 渡された1つの仕事(土台作り、計画、1つの issue の実装など)をして終わる。毎回まっさらな状態で始まる |
| GitHub | issue、PR、CI、ブランチ保護 | 仕事の一覧と進み具合を持つ。CI が合否を決める |

まとめ役は普通のシェルスクリプトで、判断はしない。決まった手順どおりに、エージェントを起動し、その最後の一行(`RESULT: ...`)を読んで次に進む。合否の判断は CI と、まとめ役が呼ぶ検査用のスクリプトがする。エージェントの自己申告は信用しない。

## 全体の流れ

```
[人間] 最初の準備
   │
   ▼
① 土台作り(bootstrap) ── アプリの骨組みと CI を作る
   │   CI そのものが正しく働くかを、わざと悪い PR を出して確かめる
   ▼
② 計画 ── 要件書を issue に分ける
   │   検査スクリプトと、別のエージェント(批評役)が確かめる
   ▼
③ 実装 ── issue を1つずつ TDD で実装し、PR を出して CI を通す
   │   ↺ 分け方が悪かった issue は、②に戻して分け直す
   ▼
④ レビュー ── 別のエージェントが /code-review し、実際に起こりうる重要な不具合だけを直す
   │   CI をもう一度通したら、まとめ役がマージする
   ▼
すべての issue が閉じたら終わり
```

途中でエージェントが自分で決められないことにぶつかると、その issue に `loop:escalated` を付けて止まる。人間がそれを見て判断する。

## 各段階の中身

### 最初の準備(人間が1回だけ)

人間が書いて固定するもの。エージェントはこれらを変えられない。

- `AGENTS.md`: エージェントが守る規則
- `docs/requirements.md`: 何を作るか
- `scripts/loop/` 以下: まとめ役、各段階でエージェントに渡す指示文、設定値、依存の許可リスト、カナリア(後述)の検査と判定のスクリプト、保護のための hook
- `.github/ISSUE_TEMPLATE/feature.md`: issue の書式。検査スクリプトがこの見出しを読む

アプリの骨組みも人間が用意する。設計の判断を含まない機械的な作業で、しかも先に Docker で動くことを確かめておけば、土台作りで無駄な試行錯誤をさせずに済むからである。

- 開発用の Docker 環境(`compose.yaml`、`docker/`、`.env.example`): `novel-site-clone` からコピーし、Compose のプロジェクト名だけを変えた(同じ名前だと、人間の版のコンテナとボリュームを取り合う)。人間の版での設計(Redis、キャッシュの破棄、デモのレート制限の環境変数など)もそのまま含んでいる
- `backend/`: `composer create-project laravel/laravel`(Laravel 13)をそのまま。生成された Laravel Boost の案内文(`AGENTS.md`、`CLAUDE.md`)は、ホストへの PHP のインストールや許可リストにない依存の追加を指示するので削除した
- `frontend/`: `create-next-app`(Next.js 16.4.6、TypeScript、ESLint、App Router、Tailwind なし)をそのまま

このため、ループの所要時間と費用には、Docker 環境と骨組みを作る分が入っていない。人間の版と比べるときは、この点を差し引いて考える。

そのうえで、GitHub にリポジトリを作り、`scripts/loop/setup-github.sh` でラベルとブランチ保護と土台作りの issue を作る。

### ① 土台作り(bootstrap)

最初のエージェントが、人間の用意した骨組みの上に、テストの道具(Pest、Larastan、Infection、Vitest、Stryker、Playwright)、worktree ごとの環境を作るスクリプト、CI をまとめて作る。普段は変更を禁じている CI やテストの設定も、この回だけは作ったり変えたりしてよい。

1つのセッションでは大きすぎるので、次の段階に分け、段階ごとに別のセッションと予算(`MAX_COST_USD_BOOTSTRAP_STAGE`)を割り当てる。どの段階も同じブランチと同じ PR に積み上げる。

| 段階 | すること |
|---|---|
| `tooling` | テストの道具と、worktree ごとの環境を作るスクリプト |
| `ci-checks` | CI のジョブ `backend` `frontend` `e2e` `mutation` `visual` |
| `ci-guard` | CI のジョブ `ac-coverage` `guard`(ずるの検出、保護パス、依存の許可リスト) |
| `finish` | metrics のワークフロー、PR のひな形、CODEOWNERS、文書。PR を開いて CI が緑になるまで直す |

段階を積み終えたらカナリアで確かめる。不合格のときは、不合格のケースを担当ごとに分け(`fix-checks` と `fix-guard`)、担当ごとに別のセッションで直してから、もう一度カナリアで確かめる。

途中で止まっても、`run.sh bootstrap` を実行し直せば、終わった段階とカナリアの round を飛ばして続きから始まる。終わった段階は `../loop-novel-site-clone.loop/bootstrap-stages.done` に記録される。

問題は、エージェントが作った CI をどう信用するかである。人間がレビューする代わりに、**カナリア**で確かめる。カナリアとは、わざと規則を破った PR のこと。たとえば次のようなもの。

- テストを飛ばす `test.skip` を入れる
- 型の検査を黙らせる `@ts-ignore` を入れる
- 既にあるテストの期待値を書き換える
- テストの無い分岐を足す
- 許可していない依存を足す

カナリアには人間は関わらない。代わりに、次のことを機械的に守らせる。

| 守りたいこと | どう守るか |
|---|---|
| CI を作る役と、CI を試す役が別である | カナリアの仕様は、土台作り役とは別のエージェント(仕様役)が書く。PR を出すのも別のエージェント(適用役)。合否はスクリプトが決める |
| 試す内容が、CI を作る前に決まっていて、後から変えられない | 仕様役は土台作りが始まる前に仕様を書く。まとめ役はその時点で仕様のハッシュ値を issue にコメントし、以後、仕様が変わっていないかを毎回確かめる |
| 土台作り役が、試す内容を見られない | 仕様はリポジトリの外に置く。作業中の見張りが、土台作り役によるカナリアの読み取りや検索を止める。まとめ役は、土台作り役の実行記録にカナリアを覗いた跡がないかを調べ、見つかればその回を無効にする。食い違いを伝えるときも、カナリアの差分は渡さず、どの規則が守られていないかだけを伝える |
| 規則に抜けがない | `AGENTS.md` の禁止事項、保護するファイル、CI の検査、依存の規則の箇条書きすべてに番号を振り、どれも1つ以上のカナリアで試されていることをスクリプトが確かめる。正しい変更が通ることを確かめるケースも必須 |
| 合否をエージェントが決めない | 判定は `scripts/loop/canaries.py` がする |

流れは次のとおり。

1. 仕様役が、`AGENTS.md` だけを読んでカナリアの仕様を書く。スクリプトが抜けを調べ、通ったら固定する。
2. 土台作り役が骨組みと CI を作り、その PR の CI を通す。
3. 適用役が、仕様どおりにカナリアの PR を出す。
4. スクリプトが結果を判定し、カナリアの PR を閉じる。すべて期待どおりなら、土台の PR をマージし、仕様と結果を PR に公開する。
5. 食い違ったら、どの規則が守られていないかを土台作り役に伝えて、2 からやり直す。

同じカナリアが何回も続けて食い違うときは、CI が悪いのか、カナリアの方が無理を言っているのかを、さらに別のエージェント(判定役)が決める。判定役は、CI の中身は見ずに、規則とカナリアの差分と結果だけを見て、「CI を直すべき」「カナリアを書き直すべき」「その規則はそもそも CI では確かめられない(免除)」のどれかを選ぶ。免除した規則は理由とともに記録する。

決められた回数をやり直しても合わないときだけ、人間に上げる。

### ② 計画

計画役のエージェントが、要件書を issue に分ける。各 issue には次のことを書く。

- 満たす受け入れ条件の ID(`AC-F5-1` など)
- 先に終わっている必要がある issue
- 触りそうなファイル
- やること、やらないこと

分けた結果は、人間ではなく2段階で確かめる。

1. **検査スクリプト**(`scripts/loop/validate-plan.sh`): すべての受け入れ条件がちょうど1つの issue に入っているか、依存が輪になっていないか、触るファイルが重なる issue どうしに順番が付いているか、などを機械的に調べる。
2. **批評役のエージェント**: 計画を書いていない別のエージェントが、要件書と見比べて、1回で終わらない issue や、抜けている依存を指摘する。

指摘があれば計画役が直す。決められた回数のうちに両方を通れば、まとめ役が issue に `loop:ready` を付ける。

### ③ 実装

まとめ役は、`loop:ready` が付いていて、依存する issue がすべて閉じているものを1つ選び、専用の作業場所(git の worktree)を作ってエージェントを起動する。1回の実行で1つの issue を実装し、1つの PR を出す。

エージェントは次の順で進める。

1. テストを先に書いて、落ちることを確かめる
2. テストが通る最小のコードを書く
3. 整理して、またテストを通す
4. PR を出し、CI の結果を待つ。落ちたら直して出し直す

CI がすべて通ったら、エージェントは止まる。マージはまとめ役がする。まとめ役はエージェントの申告をうのみにせず、自分で CI の結果を確かめる。

### マージ前のレビュー

CI が通った PR は、すぐにはマージしない。実装していない別のエージェント(レビュー役)が、Claude Code の `/code-review` で PR を調べる。

レビューでは細かい指摘も多く出るが、直すのは次の3つをすべて満たすものだけにする。

- この変更が持ち込んだ、または悪化させた不具合である(元からあった不具合や、書き方の好みではない)
- 確かに起こると確認できている
- 要件書どおりに使われるこのアプリで、実際に起こりうる(ありえない入力や、範囲外の環境でしか起きないものではない)

直すときも TDD で進める。まず指摘の不具合を再現するテストを書き、落ちることを確かめてから直す。直したら、もう一度 CI を通す。

レビュー役は、すべての指摘とその扱い(直したか、直さなかったならその理由)を PR にコメントで残す。直したものがあれば、まとめ役はもう一度レビューさせる(最大2回、`MAX_REVIEW_ROUNDS`)。直すものがなくなるか、最後の回の修正が CI を通ったら、まとめ役がマージする。

細かい指摘まで直させないのは、直すたびに新しい不具合が入る危険と、手間とが増えるからである。

### 分け直し

実装の途中で「この issue は1つの PR に収まらない」「別の issue と同じファイルを触る」などと分かったら、エージェントは人間に上げずに `loop:replan` を付けて止まる。まとめ役は、ほかの実装が終わるのを待ってから、分け直し役のエージェントを起動する。分け直した結果も、②と同じ2段階の確認を通す。

## ラベルの意味

| ラベル | 意味 | 付けるのは |
|---|---|---|
| `loop:bootstrap` | 土台作りの issue | 人間(準備のスクリプト) |
| `loop:planned` | 計画したが、まだ確認を通っていない | 計画役 |
| `loop:ready` | 確認を通り、着手してよい | まとめ役だけ |
| `loop:in-progress` | エージェントが作業中 | まとめ役だけ |
| `loop:replan` | 分け方が悪く、分け直しが要る | 実装役 |
| `loop:escalated` | 人間の判断が要る | エージェントかまとめ役 |
| `loop:canary` | カナリアの PR。マージしない | 適用役 |

## ずるを防ぐしくみ

人間がコードを読まないので、エージェントが「正しく作る」のではなく「検査を通すだけ」に走ることを防ぐ必要がある。そのために4重の守りがある。

1. **規則**(`AGENTS.md`): テストを飛ばす、検査を黙らせる、テスト環境でだけ動きを変える、といった行為を禁じている。
2. **作業中の見張り**(`scripts/loop/guard-hook.py`): エージェントがファイルを書き換えようとするたびに呼ばれ、守るべきファイル(既存のテスト、検査の設定、規則、要件書など)への変更をその場で止める。まとめ役が毎回外から差し込むので、エージェントが外すことはできない。シェルのコマンドについては推測で判定しているので、抜け道は残る。
3. **CI**: テスト、静的解析、E2E テスト、ミューテーションテスト(コードをわざと壊して、テストがそれを見抜けるかを試す)、見た目の比較、受け入れ条件ごとのテストの有無、禁止パターンの検出。最後の砦はここ。
4. **ブランチ保護と CODEOWNERS**: CI が通らない PR はマージできない。守るべきファイルを含む PR は、人間の承認がないとマージできない。

そして、3 の CI が本当に働いているかは、土台作りのときにカナリアで確かめておく。

## 人間に回ってくるとき

エージェントは次の場合に止まり、issue に `loop:escalated` を付けて、試したこと、失敗した検査とエラー、止まった理由、人間に決めてほしいことをコメントに書く。

- 要件書の受け入れ条件があいまい、または互いに食い違う
- 既にあるテストを変えないと進めない
- 既にあるテーブルや列を変える、または消すマイグレーションが要る
- 許可リスト(`scripts/loop/dependencies.md`)にない依存が要る
- 過去の設計判断(`docs/adr/`)と食い違う
- カクヨムの画面で、承認が要る操作をしたい(`docs/kakuyomu-reference.md`)
- 同じ検査が同じエラーで3回続けて落ちた、2回続けて変更がほとんど進まなかった、試行回数か費用の上限に達した

人間は、コメントを読んで判断し、必要なら要件書や規則を直す。そのあと `loop:escalated` を外して `loop:ready` を付け直せば、次の実行で続きから再開する。作業途中のブランチは残っているので、エージェントはそこから続ける。

## 動かし方

```bash
# 1. scripts/loop/config の CODEOWNER に自分の GitHub のユーザー名を入れる
# 2. git の初期化、GitHub へ push
git init -b main && git add -A && git commit -m "初期設定"
gh repo create <名前> --private --source . --push
# 3. ラベル、ブランチ保護、土台作りの issue を作る
scripts/loop/setup-github.sh
# 4. 最初は土台作りだけを動かして、結果を確かめる
scripts/loop/run.sh bootstrap
# 5. 問題なければ、計画と実装へ
scripts/loop/run.sh plan
scripts/loop/run.sh work
```

`scripts/loop/run.sh all` は、土台作り、計画、実装を止まらずに続けて行う。

`work` は、着手できる issue がなくなると止まる。全部終わったときは終了コード 0、人間の判断待ちの issue が残っているときは 2 を返す。

## 利用上限に当たったとき

claude.ai のサブスクリプションで動かすと、5時間ごとや週ごとの利用上限に当たって、エージェントが途中で止まることがある。まとめ役はこれを人間の判断待ちにはせず、次のように扱う。

1. Claude Code の出力から、上限に当たったことと、上限が明ける時刻を読み取る。時刻が分からなければ30分待つ。
2. 明ける時刻まで待つ。待っている間は、新しい issue に手を付けない。
3. 同じセッションを再開(resume)し、「待っている間に状況が変わっているかもしれないので、CI や PR の状態を確かめてから続けて」と伝える。

待つのは最長8日まで(`RATE_LIMIT_MAX_WAIT_HOURS`)。それより先にしか明けないときは、あきらめて人間の判断待ちにする。混雑やネットワークの不調など一時的なエラーのときは、5分おきに3回までやり直す。

## 記録

- エージェントの1回ごとの実行記録は `../loop-novel-site-clone.loop/logs/` に残る。再開した場合も、1つのファイルにつなげて残す。
- まとめ役は、マージの直前に、その issue にかかった時間、やりとりの回数、API に換算した費用、再開した回数を PR にコメントで残す。CI がそれを `metrics` ブランチの `metrics/metrics.jsonl` に書き足す。比較にはこれを使う。

## わかっている問題

- **利用上限の検出**: 上限に当たったことは、Claude Code が出す `rate_limit_event` とエラーの文言から見分けている。偽の Claude Code を使った試験では動いたが、本物の上限に当たったときの出力では、まだ確かめていない。見分けられなかった場合は、従来どおりその issue が人間の判断待ちになる。
- **費用の上限**: `MAX_COST_USD` は API に換算した額で、サブスクリプションで実際に払う額ではない。サブスクリプションのときにこの上限が効くかどうかは、まだ確かめていない。また、resume した実行の費用が、その回の分だけなのか、セッション全体の累計なのかも確かめていない。累計だった場合は、合計を多めに数えることになる(止まるのが早くなる方向なので、危険はない)。
- **ブランチ保護**: 「承認は不要、ただし守るべきファイルを含むときは CODEOWNERS の承認が要る」という設定が、意図どおりに効くかはまだ確かめていない。また、PR を出すのは自分のアカウントなので、守るべきファイルを含む PR は自分では承認できず、管理者としてマージすることになる。
- **並列実行**: ブランチ保護で「main に追いついていること」を求めているので、並列数を2以上にすると、先にマージされた変更に追いつけずにマージが失敗する。いまは並列数1で動かす前提。
- **シェルの見張り**: 作業中の見張りは、シェルのコマンドについては文字列から推測しているだけで、抜け道がある。最後に止めるのは CI である。
- **カナリアの隠し方**: 閉じたカナリアの PR は GitHub 上に残る。土台作り役が PR の一覧を取れば、題名は見えてしまう。差分を開けば実行記録の監査で見つかるが、題名だけから察することまでは防げない。
